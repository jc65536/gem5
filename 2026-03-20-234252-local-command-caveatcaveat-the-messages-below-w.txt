  Analysis: Why PHAST Performs 100x Worse Than Store Sets

  The key stat to explain is 9735 memory order violations (PHAST) vs 84 (Store 
  Sets). Each violation triggers a pipeline squash, causing re-execution of
  loads (136k squashed loads → 282k total loads vs 160k). This cascading
  re-execution destroys IPC.

  Root Cause 1: Store distance calculation is broken on SQ wraparound (CRITICAL)

  In phast.cc:127:
  actual_store_dist = load_inst->sqIdx - store_inst->sqIdx;

  sqIdx is a modular value (0 to SQ capacity−1), set at lsq_unit.cc:345,408:
  - Loads: sqIdx = storeQueue.tail() + 1  (modular)
  - Stores: sqIdx = storeQueue.tail()  (modular)

  When the circular SQ wraps around, this subtraction gives negative results.
  For example, with SQ capacity 114:
  - Load sqIdx = 3, Store sqIdx = 112
  - actual_store_dist = 3 - 112 = -109

  Since sqIdx is ssize_t (signed, dyn_inst.hh:357), this is -109. The clamp
  check if (actual_store_dist > 127) at line 133 doesn't catch negative values.
  The negative distance is cast to uint8_t storeDist (wrapping to 147),
  corrupting the prediction entry.

  At prediction time in storeDistToSeqNum(), this corrupted distance (147) is
  subtracted from sqIt._idx, producing an out-of-range index. dereferenceable()
  returns false, storeDistToSeqNum returns 0, and no dependency is predicted.
  The load executes speculatively and violates when the real conflicting store
  resolves.

  This single bug can explain the majority of the 100x violation increase, since
   the SQ wraps frequently during execution.

  Root Cause 2: Predictor is trained at detection time, not commit time (HIGH 
  IMPACT)

  long paths that are not leading to actual dependencies."

  Currently, violation() is called from iew.cc:1334 via instQueue.violation() →
  memDepUnit.violation() → phastPred.violation(). This happens at detection time
   (when a store executes and finds a younger load at the same address), not at
  commit.

   stores to the same address:
  - With eager training (current): the first store to execute triggers training,

  Training at detection means PHAST sees case (d) violations and learns
  incorrect dependencies.

  ---
  How Violations and Squashes Work in gem5 — Step by Step

  Step 1: Violation Detection (in IEW execute stage, iew.cc)

  The IEW stage executes instructions one at a time in executeInsts() (line
  1190+). For each memory instruction:

  - Loads: calls ldstQueue.executeLoad(inst) (line 1213)
  - Stores: calls ldstQueue.executeStore(inst) (line 1229)

  Step 2: Store execution checks the load queue (lsq_unit.cc)

  When a store executes (executeStore, line 692), it computes its effective
  address, then calls checkViolations(loadIt, store_inst) at line 749. This
  walks the load queue looking for younger loads that already executed and
  accessed the same address (lines 542-612).

  If a matching load is found (line 553), and the FWD filter doesn't skip it
  (line 585), memDepViolator is set to that load (line 600), memOrderViolation
  stat is incremented (line 602), and a fault is returned.

  Step 3: IEW checks for violations AFTER each instruction executes 
  (iew.cc:1318)

  After executing each instruction, IEW checks ldstQueue.violation(tid) (line
  1318). This simply checks if memDepViolator is non-null (set in step 2).

  If a violation exists:

  Line 1324: Gets the violating load via getMemDepViolator() (which clears the
  signal).

  Line 1334: instQueue.violation(inst, violator) — this calls
  memDepUnit.violation(store, load), which calls phastPred.violation(store, 
  load). This is where PHAST is trained.

  Line 1337: squashDueToMemOrder(violator, tid) — this does NOT squash
  immediately. It writes to toCommit->squash[tid] = true with the violator's
  seqNum (line 509-511) and sets includeSquashInst = true (line 516). This is a
  signal through a time buffer to the commit stage.

  Step 4: Commit receives the squash signal NEXT CYCLE (commit.cc:786)

  The commit stage checks fromIEW->squash[tid] (line 786). If set:

  Line 809-819: For memory violations (mispredictInst == NULL), it restores the
  PHAST branch counter.

  Line 825: Sets commitStatus[tid] = ROBSquashing.

  Line 839: rob->squash(squashed_inst, tid) — marks ROB entries for squashing.

  Line 844: Signals back to IEW via toIEW->commitInfo[tid].squash = true.

  Step 5: The actual squash propagates over subsequent cycles

  The squash signal propagates: commit → IEW → rename → decode → fetch. Each
  stage squashes its local state. The violating load and everything younger is
  re-fetched.

  ---
  Key Insight: PHAST Training Timing

  PHAST is trained at step 3 — instQueue.violation(inst, violator) at
  iew.cc:1334. This happens during the IEW execute stage, the same cycle the 
  store executes and detects the violation. The squash hasn't happened yet (it's
   just been signaled to commit).

  This is eager training at detection time. The squash won't take effect until
  the next cycle (when commit processes it). But the predictor has already been
  trained.

  Now critically — this is also before the squash removes younger instructions.
  Other stores that are younger than the violating store but older than the
  violating load might still be in the pipeline, not yet executed. If one of
  those stores ALSO conflicts with the same load (and is the younger/correct
  dependency per the paper), PHAST will never see it because:

  1. The violation is detected by the first conflicting store to execute
  2. PHAST is trained with that store's distance immediately
  3. The pipeline squashes from the violating load
  4. The younger conflicting store is squashed before it can execute

  On re-execution, PHAST predicts the load should wait for the older store
  (learned in step 2). The load waits for it, then executes. But now the younger
   store resolves and detects ANOTHER violation — because the load executed
  after the older store but before the younger store. This triggers another
  squash and another training, this time with the younger store's distance.

  This cascading pattern continues until PHAST learns the youngest conflicting
  store. The paper avoids this by using lazy squash — waiting until commit, when
   ALL conflicting stores have resolved, and only training with the youngest
  one.

  logged as "FN".

  But a load that received forwarding after being predicted independent is NOT 
  necessarily a false negative. The load might have been predicted independent,
  executed, and happened to read from a store that forwarded to it — but the
  load was never in danger of violating because the store executed before the
  load. The forwarding happened naturally through the SQ search, not because the
   load overtook the store.

  A true False Negative is: PHAST predicted no dependency, the load executed
  speculatively, overtook a conflicting store, and caused a memory order
  violation. But those loads get squashed and never reach commit. So
  updateConfidence cannot observe true FNs at all.

  The "FN" log at line 318 is really logging: "no dependency predicted, but the
  load happened to receive forwarding from some store." This isn't actually a
  misprediction — it's a load that executed fine (no violation) and happened to

  Lines 327-338 handle loads with a prediction. The check:

     Lazy Squash for PHAST Memory Order Violations

     Context

     With eager squash (current), only the first conflicting store triggers a
     violation before the pipeline flushes. Younger conflicting stores are
     squashed before they can execute. This causes cascading violations: PHAST
     learns the wrong (older) store, re-executes, and a younger store fires
     again. This repeats until the youngest store is learned, producing 100x
     more violations than Store Sets.

     The PHAST paper uses lazy squash (Section V): violations are flagged but
     the pipeline continues, allowing ALL conflicting stores to execute. At
     commit, the youngest conflicting store is known, PHAST trains correctly,
     and one squash handles the entire dependency. This eliminates cascading.

     Note: This supersedes the lazy training change (which deferred training to
     commit but still used eager squash). With lazy squash, the training
     naturally happens at commit since that's where the squash occurs.

     Approach

     For PHAST only (Store Sets keeps eager squash):
     1. checkViolations flags the load instead of triggering an immediate squash
     2. Multiple stores can update the flag, keeping the youngest
     3. IEW never sees a PHAST violation (no memDepViolator, no fault)
     4. At commit, when a flagged load reaches the ROB head, squash and train
     PHAST

  uint32_t Phast::foldHistory(uint64_t load_branch_count, int hist_len) const {
      hist_len += 1;
      uint32_t folded = 0;
      for (int i = 0; i < hist_len; ++i) {
          if (load_branch_count <= i) break;
          uint64_t idx = load_branch_count - 1 - i;
          if (idx < ghbCounter - ghbSize) break;  // ← THE BUG
          uint8_t branch_hist = globalHistoryBuffer[idx % 512];
          ...

  }

  At decode time (when checkInst runs), ghbCounter is close to
  load_branch_count, so idx is within the valid GHB window. The hash is computed
   correctly.

  At commit time (when violation() runs — whether eager from IEW or lazy from
  commit), ghbCounter has advanced by thousands since decode. For example:
  - load_branch_count = 100 (at decode)
  - ghbCounter = 100000 (at violation time, many iterations later)

  - idx = 99 → 99 < 99488 → loop breaks immediately

  wrong table location. On the next decode, checkInst can't find it.

  - ~10k violations persist regardless of eager/lazy training
  - The predictor never effectively learns despite being trained
  - The problem exists in both the original and modified implementations

  design tradeoff: serialize stores to simplify the prediction mechanism.

   doesn't need stores to execute in order because it directly identifies which
  store the load depends on.

❯ About the lru logic in phast.cc: would it be beneficial to make the entry     
replacement policy rely on confidence instead of lru?                           

⏺ Yes, it would be better — but only after the confidence mechanism is fixed.
  Here's why:

  With correct confidence: Confidence-based replacement is strictly better than
  LRU. A low-confidence entry is likely a stale or wrong prediction — it should
  be the first to go when a new violation needs space. A high-confidence entry
  is a proven, frequently-correct prediction that should be preserved. LRU can
  evict a high-confidence entry just because it wasn't accessed recently (e.g.,
  a dependency that fires every Nth iteration).

  With the current broken confidence: It would make things worse. Valid entries
  get their confidence incorrectly drained to 0, and confidence-based eviction
  would then prioritize evicting those "low confidence" entries — which are
  actually correct predictions being falsely penalized.

  The paper uses LRU (Section IV-B: "a 2-bit field for the less-recently-used 
  (LRU) replacement policy"), but the paper also has a working confidence
  mechanism. A practical improvement over the paper would be: evict 
  lowest-confidence first, break ties with LRU. This combines the benefits of
  both.

  I'd suggest: fix the confidence check first (using the diagnostic stats from
  the current run), then switch replacement to confidence-based. The two changes
   together would reinforce each other — correct confidence means correct
  eviction priorities.

❯ I noticed that for the benchmarks with more numFPDifferentStore (thus         
decreased confidence), there are thousands of memOrderViolations, while for     
benchmarks dominated by numFPNoForwarding (very little decrement), there are    
only hundreds. Why does it seem like decrementing confidence results in more    
violations?                                                                     
⏺ Because it creates an oscillation cycle:

  1. Entry has confidence > 0 → load waits for predicted store → gets forwarding
   from a different store → confidence--
  2. After 15 decrements → confidence = 0 → entry disabled
  3. Load has no prediction → executes speculatively → violation
  4. Violation re-trains entry → confidence = MAX
  5. Back to step 1

  The key insight: the DifferentStore predictions are "wrong" but harmless. The
  load waited for store S1, got data from younger store S2 instead. The load
  committed successfully — no violation. Decrementing confidence for this case
  is counterproductive because disabling the entry leads to actual violations,
  which are worse than the harmless false positive.

  Think about it: a load that waits for the "wrong" store but commits fine has a
   small cost (unnecessary stalling until S1 executes). A load with NO
  prediction that violates has a large cost (pipeline squash). The confidence
  mechanism is trading a small cost for a large one.

  The fix: don't decrement confidence for any committed load. If a load reaches
  updateConfidence, it committed without violations — the prediction was either
  correct or harmlessly conservative. Only let entries be replaced through the
  eviction policy (lowest confidence first, which now means entries replaced by
  newer violations).

❯ so what is the purpose of confidence in the paper?                            

⏺ The paper uses confidence to remove stale entries that cause false positives
  (unnecessary stalling). From Section IV-A2:

  ▎ "The confidence counter is used to disable aliased dependencies that cause 
  mispredictions."

  In the paper's simulator, the confidence check works correctly because:

  1. Lazy squash — the load commits only after ALL conflicting stores have
  resolved. The forwarding store is reliably the youngest conflicting store.
  2. SQ lifetime — in their simulator, the SQ entry persists until the
  forwarding check completes. forwardingStoreSeqNum always matches
  predictedStoreSeqNum for correct predictions.
  3. No "store committed early" problem — their forwarding path doesn't have the
   race where the store leaves the SQ before the load reads from it.

  So in their simulator, forwardingStoreSeqNum ≠ predictedStoreSeqNum genuinely
  means the prediction was wrong (aliased entry pointing to a store at the wrong
   address). Decrementing is correct — it removes the aliased entry, and the
  next violation trains the right one.

  In our gem5 implementation, the same check produces false mismatches because:
  - The store commits and leaves the SQ before the load executes →
  forwardingStoreSeqNum = 0
  - A younger store at the same address forwards instead → forwardingStoreSeqNum
   ≠ predictedStoreSeqNum

  Both are "correct" predictions in practice (the load got correct data, no
  violation), but the check sees them as wrong.

  To properly implement confidence, we'd need to match the paper's simulator 
  semantics — specifically, ensuring forwardingStoreSeqNum reliably reflects
  which store the load actually depended on. That would require keeping the
  store's SQ entry alive until the dependent load executes, which is a deeper
  change to the LSQ.
